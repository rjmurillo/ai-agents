# analysis-provenance

Tells you who owns a validator, linter, or tool config before you edit it. It labels the target `UPSTREAM`, `LOCAL`, `VENDOR`, or `UNKNOWN` and says whether to change the file or its configuration.

## When to use it

- You plan to change how a validator or linter behaves.
- You plan to edit a tool configuration file or analyzer settings.
- A validation failure surprises you and you want to know who owns the check.
- Trigger phrases: `check provenance before modifying`, `is this file upstream or local`, `who owns this validator`, `check code ownership`, `analyze provenance`.

## When not to use it

- You want to configure or modify style validators: use [`style-enforcement`](style-enforcement.md).
- You want to evaluate an external solution: use [`programming-advisor`](programming-advisor.md).
- You want a broad codebase investigation: use [`analyze`](analyze.md).

## Quick start

In Claude Code, after a plugin install, run:

```text
/project-toolkit:analysis-provenance .config/markdownlint.json
```

In GitHub Copilot CLI, or in a Claude Code session inside a checkout of this repository, drop the prefix: `/analysis-provenance .config/markdownlint.json`.

The skill reports a category, a confidence, the evidence behind it, and a recommendation.

## What you get

| Category | Meaning | Action |
| --- | --- | --- |
| `UPSTREAM` | External dependency (npm, pip, NuGet) | Configure it. Do not modify it. |
| `LOCAL` | Project-owned code | Modify as needed. |
| `VENDOR` | Copied or vendored upstream code | Avoid modifying. Track upstream. |
| `UNKNOWN` | Cannot determine | Investigate before modifying. |

Text output looks like this:

```text
Provenance Check: node_modules/markdownlint-cli2/lib/main.js
============================================================
Category: UPSTREAM
Confidence: HIGH
Evidence:
  - Located in node_modules directory
Recommendation: Do NOT modify. Configure via .markdownlint.json instead.
```

For an `UPSTREAM` result, adjust local configuration, look for an override option, and document why a rule is suppressed if no override exists.

## Advanced use

The script resolves the target, then checks dependency directories (`node_modules`, `.venv`, `vendor`, `.gitmodules`), package manifests and lockfiles, and the first 20 lines of the file for generated markers and copyright notices. It weighs those signals and returns a category with evidence.

Run it from the root of a checkout of this repository:

```bash
uv run python .claude/skills/analysis-provenance/scripts/check_provenance.py --target .config/ --format json --verbose
```

| Flag | Meaning |
| --- | --- |
| `--target` | File or directory to analyze. Required. |
| `--format` | `text` or `json`. |
| `--verbose` | Include detailed evidence. |

The script exits 0 when it determines provenance and 1 when the target is not found.

Typical signals: `UPSTREAM` files sit under `node_modules/`, `.venv/`, `site-packages/`, `.nuget/`, or a git submodule path, or carry a "Generated by" or "DO NOT EDIT" header. `LOCAL` files sit under the project root, outside dependency directories, tracked in git. `VENDOR` files sit under `vendor/`, carry a "Vendored from" comment, or have a `VENDORED.md` beside them. Linter config files such as `.markdownlint.json`, `.eslintrc.json`, and `.editorconfig` are usually `LOCAL`.

The [`build`](build.md) skill invokes this one in its Phase 2b, to classify each validation target before Phase 3 edits it.
