# Retrospective: ADR-109 shipped six classes in four days, but the install tree was incomplete for 84 of 111 skills until a smoke test caught it at the last step

**Date**: 2026-09-16
**Scope**: ADR-109 template-first plugin distribution, full program. PR #5745 (ADR accepted, `8ff9e734b`), #5755 (spec set), #5758 (B1 agents, `f50f68551`), #5775 (B2 rules, `084f89340`), #5773/#5780/#5781/#5782/#5783 (B3 skill batches, five PRs), #5785 (B3 render-target move and pilot pin retirement, `23c3d5dd3`), #5794 (B3 skill support-file mirror, `77a44751b`), #5784 (B4 hooks and settings, `9bf7c7c3a`), #5787 (B5 lib mirror, `4d83781fe`), #5791 (B6 marketplace switch, `a655779a5`, closes #5282), #5777 (program handoff). All merged 2026-09-12 through 2026-09-15.
**Failure mode classification**: false completion markers (`.agents/governance/FAILURE-MODES.md`); a task's acceptance criteria described a narrower artifact than the consumer it was meant to satisfy.

## What happened

ADR-109 moved six artifact classes (agents, rules, skills, hooks, lib, the marketplace manifest) from hand-maintained `.claude/` files to `templates/` as the single canonical source, rendered into a new `src/claude/` plugin tree, then binplaced back into `.claude/` for repo-local use. Eleven PRs landed the program in four days. Execution model: Sonnet subagents built each PR and its review-round fixes in sibling worktrees, with batches 2 through 5 of the skills class running in parallel on separate branches; Opus, as coordinator, reviewed each diff, probed the drift gates by hand against the live tree rather than trusting a subagent's pass claim, merged, and re-merged `main` into every branch still open.

The program's own task file scoped skill migration at the `SKILL.md` level only. TASK-033 (`.project-toolkit/specs/tasks/TASK-033-remaining-skills-migration.md`) and DESIGN-025 (`.project-toolkit/specs/design/DESIGN-025-template-first-compiler-and-binplace.md:59-60`) both describe the skills row's plugin-tree target as `src/claude/skills/<name>/SKILL.md`, and no acceptance criterion required install parity for a skill's `scripts/`, `references/`, or `tests/` directories until TASK-033 added one retroactively (`.project-toolkit/specs/tasks/TASK-033-remaining-skills-migration.md`, the "2026-09-15 follow-up" bullet). B3 (PR #5785) rendered only `SKILL.md` into `src/claude/skills/`. Eighty-four of 111 skills also carry support files under `.claude/skills/<name>/` (43 with scripts, 61 with references, 36 with tests, per PR #5794's body), and none of those reached the plugin tree. No gate caught the gap: `build_all.py --check` exited 0, because nothing in its allowlist named the support files as owned. It surfaced only when B6's install-verification step ran `RUN_CLI_E2E=1 uv run pytest tests/e2e/test_plugin_load_smoke.py -k claude` against the marketplace source repointed at `src/claude`, the first point in the program where a real plugin install was exercised end to end. Fixed in PR #5794 (`77a44751b`), which mirrored 525 files in one commit.

The first version of PR #5794's fix introduced a second defect: `build/scripts/skill_support_mirror.py`'s `--check` mode wrote for real on every run and reported "526 written" whether the tree was clean or not, so an uncommitted hand edit to a mirrored file was silently overwritten back to canonical content and an untracked extra file was silently deleted, both before the git-diff staleness check ran. The Opus coordinator's live probe against the pushed tree (append a line to a tracked file, run `--check`, observe it get corrected instead of reported) found this; the PR's own unit tests had passed because they seeded a synthetic repo that did not reproduce the real tree's starting state. Fixed same-day in commit `4c51fe4c4`, which added a read-only `check=True` mode to the shared `_copy_skill_tree` routine and a compare-before-write guard.

## Impact

| Area | Severity | Effect |
|---|---|---|
| Plugin install (real consumers) | High | `project-toolkit` installed from `src/claude` would have shipped SKILL.md files pointing at scripts that did not exist on disk, for 84 of 111 skills, had B6 merged before #5794 |
| Build gate integrity | High | A `--check` mode that always writes and always reports success is worse than no gate: it hides drift instead of reporting it |
| CI on open PRs | Medium | Every `main` edit to a template-owned file (rules, autoplan, benchmark-models) turned an open B-series branch red with DRIFT until the branch merged `main` and re-rendered from the merged state |
| Bot review volume | Medium | CodeRabbit re-reviewed every push across eleven PRs; verified GraphQL thread counts: 28 on PR #5787 (B5), 26 on PR #5784 (B4), 10 on PR #5791 (B6) |
| Wall clock | Low | Program landed in four days (2026-09-12 to 2026-09-15) across eleven PRs; the support-file gap added one same-day follow-up PR (#5794) plus one same-day fix commit (`4c51fe4c4`) rather than a second review cycle |

## Root causes

1. **A spec described the render target at the file level, not the consumer level.** TASK-033's original scope named `src/claude/skills/<name>/SKILL.md` as the thing to move; it did not ask "what does a plugin installed from this tree need to run," which would have surfaced the support files immediately. The gap closed only when a later acceptance criterion (added the same day the install-verification test ran) asked the consumer-facing question directly.
2. **`build_all.py --check`'s allowlist and its correctness were never tested against the shape of the real tree.** The first `--check` implementation for the new mirror passed its own unit tests because those tests constructed a repo that did not match the live repository's starting state (a tree with 525 already-correct files versus one built from scratch). A claim that a gate passes is evidence about the test fixture, not about the tree the gate will actually run against.
3. **CI evaluates the merge of a PR's head with `main`, and template-owned files kept moving on `main` while five skill batches ran in parallel.** Each batch widened the same `PILOT` pin in `tests/build_scripts/test_skill_templates_pilot_scope.py` on its own branch; landing them required merging `main` into each remaining open branch and taking the union of both sides' names, not either branch's copy alone (verified: PR #5780's body states "79 after merging main, which carries batch 4"; PR #5781's body states "111, the full skill set, after merging main, which carries batches 2, 4, and 5"). The first attempt on B2 (rules) instead took `main`'s copy of a file wholesale and overwrote branch-side citation re-anchors; the correct move, established after that miss, was always to merge and re-render from the merged state.
4. **Byte-copied content gets reviewed as new content.** Moving existing `.claude/` files into `templates/` verbatim still triggers a full bot review of the copy, because the review tooling has no way to know the content predates the PR. This produced two kinds of findings: real, previously-undiscovered issues in code that happened to get its first fresh look in years (a Semgrep-flagged `tempfile.mktemp` race in `scripts/github_core/discourse_traversal.py`, fixed by switching to `tempfile.NamedTemporaryFile(dir=path.parent, delete=False)` per PR #5787's body; a merge-resolver add/add conflict handler in `.claude/skills/merge-resolver/scripts/resolve_pr_conflicts.py` that silently discarded the head branch's own evidence record instead of blocking, the same defect class that caused the PR #4856 collision, fixed in PR #5781 to block instead; a 179-line truncation of `windows-image-updater/SKILL.md` dating to PR #1695, restored from its pre-truncation 2026-03-23 revision `2d8b8838e` in PR #5782), and prose-quality findings on rule text that had nothing to do with the migration (nine findings on PR #5775, filed to issue #5778 rather than fixed inline, to keep the B2 migration lossless).

## What worked

- **Live-probing a gate instead of trusting a pass claim caught both defects in this retrospective's scope.** The coordinator's hand probe against the pushed tree, not a subagent's report or a passing unit test, is what found the skill-support gap's downstream `--check` bug. The B1 retrospective (`.project-toolkit/retrospective/2026-09-14-adr-109-b1-agent-templates.md`) recorded the same pattern one class earlier: a parity gate that could not fail kept reporting PASS until an independent review probed it with real inputs.
- **A regression test seeded from the live tree's actual shape, not a synthetic one, is what the fix needed and got.** PR #5794's follow-up commit `4c51fe4c4` added tests "pinned to fail against the pre-fix code, pass after," seeded to match the live tree's layout rather than a hand-built fixture, closing the exact gap the first version's tests missed.
- **Merging `main` into every open branch before landing, every time, kept the parallel skill batches from clobbering each other.** Five batches ran concurrently on separate branches; each merge took the union of both sides' `PILOT` pin widenings rather than either side's copy, and the one deviation from that rule (B2 taking `main`'s file wholesale) was caught and is now the negative example to avoid.
- **Deferring prose-only findings to a follow-up issue kept the lossless migration lossless.** PR #5775's nine CodeRabbit findings on pre-existing rule text went to issue #5778 instead of being fixed inline, so B2's diff stayed a verified byte copy and did not mix migration with content editing.
- **The program stayed inside its four-day window despite the mid-program gap.** The fix for the support-file gap landed same-day as the PR that introduced it, as a follow-up PR plus one fix commit, not a second review round on a reopened PR.

## Environment notes

Background Bash jobs on the coordinator's machine were killed for low memory with no notification, which stalled several subagents waiting on a completion signal that would never arrive; the fix, applied mid-program, was running test suites in the foreground per top-level directory instead of backgrounding them (later PR bodies note runs explicitly as "foreground, no background jobs," for example PR #5794's testing section). One subagent ran `git checkout -- <file>` on a path it meant to inspect rather than revert and lost uncommitted edits to that file. One subagent committed with `--no-verify` on a commit that stayed local; the commit was reverted before the branch was pushed, so no unverified commit reached a remote branch.

- [x] `merge-resolver`'s add/add conflict handling blocks instead of silently discarding evidence under `.project-toolkit/sessions/`, `.project-toolkit/qa/`, or `.project-toolkit/retrospective/`. Evidence: PR #5781.
- [x] `discourse_traversal.py`'s checkpoint write uses `tempfile.NamedTemporaryFile(dir=path.parent, delete=False)` instead of the predictable-pathname `tempfile.mktemp`. Evidence: PR #5787.
- [x] `windows-image-updater/SKILL.md`'s 179-line truncation (PR #1695) is restored from its pre-truncation revision. Evidence: PR #5782.
- [ ] Before a future multi-class or multi-batch migration, write the render-target acceptance criterion at the level of what a consumer needs (a working install, a runnable script), not at the level of the single file the migration happens to be moving first.
- [ ] Before trusting a new `--check` mode, verify its unit tests seed a fixture that matches the real tree's starting shape, not a synthetic one built from scratch; the coordinator's live probe against the pushed tree remains the check of record regardless.

## Learning

A render target scoped to "the file this task is moving" is not the same question as "what does the consumer of this tree need to exist." TASK-033 answered the first question correctly and completely (`SKILL.md` moved, byte-identical, gate green) and still shipped an incomplete plugin tree, because the second question was never asked until an end-to-end install test asked it by construction. When a migration's acceptance criteria are written from the mover's side of the move, add one criterion from the consumer's side before calling the class done, even when every existing gate is green.
