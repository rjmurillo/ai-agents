## Phase 1: Insights Generated
### Five Whys
1. Why did the push fail after focused tests passed? The pre-push hook ran repository-wide checks.
2. Why did repository-wide checks fail? They included moving-base ratchets and tests outside the PR diff.
3. Why were those failures initially ambiguous? The hook output was not bound to the PR's captured base SHA.
4. Why is base binding necessary? The repository changes rapidly, so `origin/main` can advance during validation.
5. Why should the branch not repair those failures? They do not reproduce against the PR-bound base or arise from changed inputs.

### Fishbone
- **Environment**: Concurrent merges advanced `origin/main`.
- **Process**: Full pre-push validation compared against a moving ref.
- **Evidence**: CI logs reflected a synthetic merge tree, while focused local tests used the bound base.
- **Scope**: The PR changed output-writing code and one taste baseline, not instruction corpus inputs.

### Patterns and Shifts
- Check names are not root causes; exact failed steps and node IDs are.
- Bound identity and diff ownership are stronger evidence than a red repository-wide hook.
- Ratchets may fall for branch-owned improvements, but must not widen for inherited failures.

- Before editing a CI measurement, compare its inputs between the captured base SHA and PR head.
- Accept a branch fix only when the failure reproduces on that bound comparison or touches changed inputs.
- Record stale or inherited failures as blockers with exact node IDs.
