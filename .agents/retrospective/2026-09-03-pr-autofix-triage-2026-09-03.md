## Phase 1: Insights Generated

**Five Whys (why did the auto-generated retrospective skeleton contain fabricated history?)**
1. Why did the skeleton describe an unrelated PR (#5234/ADR-099)? `run_retrospective.py`'s Phase 0 evidence gathering reads the most recent session log under `.agents/sessions/`, and the most recent one on disk belonged to a different, earlier session.
2. Why didn't the script detect the mismatch? It has no cross-check between the session log's claimed branch/PR and the actual worktree/branch the script is invoked from.
3. Why does this matter here specifically? The retrospective is written to satisfy a gate that blocks a real push; an uncorrected skeleton would ship a false historical record under this session's authorship.
4. Why is that a live risk rather than a one-off? This is the second recorded instance of the exact same failure mode (see `2026-09-01-pr5344-...md`), so the script's evidence-gathering step reliably picks up stale session logs whenever the most recent one on disk isn't this session's.
5. Root cause: `run_retrospective.py`'s session-log discovery has no session-identity check, so its Phase 0 evidence is only as trustworthy as "most recently modified file in `.agents/sessions/`," which is a coincidence, not a guarantee, in an environment with concurrent or sequential unrelated sessions.

**Pattern**: the same gate (`retrospective-policy`) and the same script defect (session-log-derived skeleton pulling unrelated history) has now blocked two different sessions three days apart. Both were resolved the same way (hand-correct, don't bypass), which is the right per-session fix but doesn't fix the script.

## Phase 4: Extracted Learnings

### Learning 1
- **Statement**: `git_hook_policy.py`'s `retrospective-policy` pre-push gate computes its documentation-only bypass over `git diff merge-base(origin/main, HEAD)..HEAD`, not over the individual commit being pushed, so a doc-only commit on a long-lived feature branch still fails the bypass because the whole branch's non-doc diff remains in range.
- **Atomicity Score**: 80% (Accepted)
- **Evidence**: `scripts/validation/git_hook_policy.py:6359` (`resolve_push_update`, `base = _merge_base(repo_root, "origin/main", push_ref.local_sha)`); reproduced on PR #5343 branch `claude/fix-4632-build-all-check-fails-open`, commit `1b8012a2d` (2 `.md` files only) still failed `_documentation_only` because the branch's other 37 commits (mostly `build/scripts/build_all.py`) are in the same push range.
- **Skill Operation**: TAG
- **Target Skill ID**: `retrospective` (add this as a known-gate-behavior note for future sessions blocked by the same push)

### Learning 2
- **Statement**: A Copilot review thread left unresolved does not mean the underlying code is unfixed; check whether a same-session or prior-session commit already addresses it (by timestamp proximity and by reading the diff) before re-implementing, then verify with the real test suite and reply with evidence rather than assuming silence means the work is undone.
- **Atomicity Score**: 75% (Accepted)
- **Evidence**: PR #5361 threads `PRRT_kwDOQoWRls6etVW1` and `PRRT_kwDOQoWRls6etVXL`, review comments at `2026-09-02T22:41:23Z`, already fixed by commits `f6175da1f` (22:47:43Z) and `fd5885997` (22:47:28Z) on the same pushed head.
- **Skill Operation**: TAG
- **Target Skill ID**: `pr-comment-responder`
