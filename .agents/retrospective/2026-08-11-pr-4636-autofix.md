## Phase 1: Insights Generated
Five Whys: Why did the first push fail? A Ruff count baseline exceeded current
`main`. Why? The long-lived branch had not received the lowered baseline. Why
was this found late? Branch-relative ratchets ran inside pre-push after other
work. Why was the branch not refreshed first? Initial live state still reported
the older PR base SHA. Why did that remain authoritative? GitHub API state was
stale relative to the newly fetched remote base. Root cause: branch freshness
was not checked locally before the full push gate.

Fishbone: Process contributed a late base refresh. Tooling contributed an
expensive pre-push ordering. Environment contributed GitHub API rate
exhaustion. Evidence rules contributed a required follow-up after the merge.

Patterns and shifts: Long-lived PRs need local base ancestry checks before
branch-relative ratchets. QA evidence is intentionally SHA-bound, so every code
or base merge requires a new evidence binding.

Learning Matrix: Keep isolated worktrees and guarded mutations. Add an early
base freshness probe. Modify the QA evidence after every merge. Drop stale CI
assumptions.

### SMART Validation
The base freshness action is specific (`git rev-list HEAD..origin/main`),
measurable (behind count), achievable before push, relevant to count ratchets,
and time-bound to each push attempt. The QA rebinding action is measurable by
the session validator and QA report checker.

### Action Sequence
1. Fetch the base through the guarded mutation path.
2. Measure local ancestry and branch-relative ratchets.
3. Merge the current base when behind.
4. Run focused tests and quality checks.
5. Bind QA and session evidence to the latest non-evidence commit.
6. Push only after the identity-bound live-state recheck succeeds.
