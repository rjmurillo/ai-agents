## Context for Next Session

- `_collect_shas()` in `extract_session_episode.py` seeds from `episodeMetrics.commitHead` if present (a full SHA), else `episodeMetrics.comparison.head`, else `endingCommit`; it then *unconditionally* also scans `changesCommitted.Evidence` for any hex-letter-containing 7-40 character token via `_SHA_RE`/`_prose_shas`, regardless of which seed branch was taken. A session log's `changesCommitted.Evidence` field must therefore never spell out, as a bare token, a commit SHA the session did not itself produce (round-3 through round-6 rebind targets, in particular), or a future regeneration will silently reintroduce it as a fabricated commit event.
- `post_qa_code_changes()` (`.claude/lib/qa_report.py`) diffs a merge commit against *both* parents (`git log -m`), unlike `extract_session_episode.py`'s first-parent-only convention elsewhere. Any merge of `main` into this branch will restale existing QA bindings no matter how the merge is created (local push or `gh pr update-branch`); this is a property of the merged content, not a hook-bypass question. See `.serena/memories/git/git-merging-main-forfeits-the-docs-only-push-bypass.md`.
- `scripts/validation/pr_commit_count.py`'s main-merge relief (`MAIN_MERGE_BLOCK_THRESHOLD = 40`) requires the merge's non-first-parent to be on `origin/main`'s first-parent trunk; only genuine merge commits qualify, so squashing or rebasing away the merge would forfeit the relief and reintroduce the original 20-commit block.
- `QA_EVIDENCE_PREFIXES` (`.agents/memory/episodes/`, `.agents/qa/`, `.agents/sessions/`) governs staleness: any file changed outside these three prefixes, between a QA report's bound commit and the live PR head, stales every session whose QA report lists that file as evidence. `.agents/analysis/2026-08-12-adr-080-copilot-model-resolution.md` is an evidence path but not a QA-evidence-prefix path; this has now triggered rebinds three separate times (`9996e0905`, `e8b9229b9`, and now this round's fix). Any future edit to that file requires rebinding both QA reports again, in a follow-up commit.
