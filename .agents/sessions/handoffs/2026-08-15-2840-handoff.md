## Context for Next Session

- `_collect_shas()` in `extract_session_episode.py` seeds from `episodeMetrics.commitHead` if present (a full SHA), else `episodeMetrics.comparison.head`, else `endingCommit`; it then *unconditionally* also scans `changesCommitted.Evidence` for any hex-letter-containing 7-40 character token via `_SHA_RE`/`_prose_shas`, regardless of which seed branch was taken. A session log's `changesCommitted.Evidence` field must therefore never spell out, as a bare token, a commit SHA the session did not itself produce (round-3 through round-6 rebind targets, or another session's own commit, in particular), or a future regeneration will silently reintroduce it as a fabricated commit event. Round 9's `c860ae452` dual-attribution bug is exactly this failure mode, discovered by cross-referencing each session's own `workLog` narrative rather than trusting either episode's prior `episodeMetrics`.
- `post_qa_code_changes()` (`.claude/lib/qa_report.py`) diffs a merge commit against *both* parents (`git log -m`), unlike `extract_session_episode.py`'s first-parent-only convention elsewhere. Any merge of `main` into this branch will restale existing QA bindings no matter how the merge is created (local push or `gh pr update-branch`); this is a property of the merged content, not a hook-bypass question. See `.serena/memories/git/git-merging-main-forfeits-the-docs-only-push-bypass.md`.
- `scripts/validation/pr_commit_count.py`'s main-merge relief (`MAIN_MERGE_BLOCK_THRESHOLD = 40`) requires the merge's non-first-parent to be on `origin/main`'s first-parent trunk; only genuine merge commits qualify, so squashing or rebasing away the merge would forfeit the relief and reintroduce the original 20-commit block.
