# Test File Rules

Tests under `tests/`, skill `tests/` directories, and `.agents/security/benchmarks/` enforce correctness and catch regressions. They are not decoration.

## MUST

1. **Structural validation**. Quality-gate prompt tests MUST comply with ADR-023 structural requirements. Other tests follow the placement and coverage rules below.
2. **Pester version**. PowerShell tests MUST target Pester 5.7.1+. Python tests MUST target pytest 8+.
3. **Evidence for fixture changes**. MUST NOT modify baseline fixtures to make failing tests pass. A baseline change MUST cite the behavior change that justifies it.
4. **Coverage targets**. Coverage MUST meet category minimums (`AGENTS.md`): 100% security, 80% business, 60% docs.
5. **Independent tests**. Each test MUST pass in isolation. Shared mutable state is prohibited.
6. **Placement**. New tests MUST live in `tests/` or `.agents/security/benchmarks/`. Do not add tests to shipped skill directories.
7. **A mutation harness MUST report three outcomes, not two**. DEAD, SURVIVED, and **DID-NOT-APPLY**. The conventional reading of a mutation result is that a survivor means a weak test. That reading is unsafe here, because the common cause of a survivor in this repository is that the mutation never applied: the target literal had moved or been reworded, the patch step wrote nothing, the file stayed byte-identical, and the harness then graded unmutated code and printed SURVIVED. A harness that cannot tell those apart reports the same string for "your test is weak" and "I tested nothing." Each mutant MUST count occurrences of its target before patching and refuse an ambiguous or absent match, MUST exit non-zero from the patch step when the literal is missing, MUST `cmp -s` the patched file against a backup and fail when they match, and MUST assert a byte-identical restore afterward. Measured: one harness reported four survivors of which three had silently failed to apply, and a second reported a clean sweep it had never performed.
8. **Assert on the process exit code, not on a helper's return value**. A test for a CLI or a gate MUST drive `main(argv)` (or the documented entrypoint) and assert on the integer it returns or the process status it produces. Asserting that a helper returned a findings list, an error string, or a falsy sentinel proves the helper detected the problem and proves nothing about whether the program fails. This is the dominant silent-pass shape in this repository (Issue #4068, six confirmed instances): a `run:` block under `set -e` fails on any non-zero exit, the natural Python translation returns a sentinel instead, no caller converts it, and the step goes green on a failure that used to be red. Every affected case had passing tests, and every one of those tests asserted on a return value.
9. **Assert on parsed structure, never on a substring of a structured file**. A test that checks wiring in YAML, JSON, or TOML MUST parse the document and assert against the resulting object graph. `assert "some-step-name" in workflow_text` passes when the step has been deleted and the name survives in a comment, an adjacent job, or an unrelated key, and a fixed-width text window around a match reaches into the neighbouring block. Measured: a wiring test passed after a mutant removed the step's `- name:` line, and a ratchet-wiring test passed with both ratchets commented out.
10. **A scope measurement MUST be reported together with the size of the scope**. When a change narrows what a checker examines, the count of findings alone cannot distinguish "nothing is wrong" from "nothing is being checked", because the filter under evaluation is also the filter applied to the evidence. State how many candidates were examined next to how many failed, and MUST NOT cite a zero-finding result whose examined count is unknown. Measured: a configuration change was accepted on a `Summary: 0 issues` line while `Linting: 0 files` sat directly above it; the same tool on the same tree reported 823 issues across 141 files once the scope was restored.
11. **A mutation harness MUST include at least one inverted control**: a mutation the suite is required to SURVIVE, asserted as `rc == 0`. A harness whose mutants are all the same polarity, apply a change and expect failure, cannot distinguish "every mutant died" from "the harness fails no matter what." Any defect that makes the run fail unconditionally reads as a clean sweep. Measured: a harness passed pytest a dotted module name as a positional argument, pytest read it as a filesystem path, every invocation exited 4 with `file or directory not found` having collected zero tests, and four mutants asserting only `returncode != 0` each reported a kill; the harness graded a suite it had never once run. Adding one mutant that must survive surfaced it on the first execution. A harness that shells out to a test runner MUST also reject the runner's silent-nothing-ran signals directly, at minimum `"no tests ran"` absent from the output and a `returncode` that is not pytest's usage-error 4, and MUST target test files by filesystem path rather than by dotted module name.
12. **When a change alters concurrency or synchronization semantics, one green run is not evidence. Stress-run it.** The conventional reading of a passing suite is that the change is safe. That reading does not hold here, because a single run samples one interleaving and the suite reports it as though it had sampled the space. The trigger is any change to how work is scheduled or serialized; introducing or resizing a thread or process pool, moving work onto an event loop or a queue, adding or removing a lock, and fanning out through `asyncio.gather`, `Promise.all`, or goroutines are examples rather than the whole list. Such a change MUST have the affected tests run at least thirty times in a row, and any failure in that window MUST be treated as a defect in the test or in the code rather than as noise. Thirty is not arbitrary: `n` runs miss a defect that fails on a fraction `p` of interleavings with probability `(1-p)^n`, so twelve runs miss a one-in-ten flake 28 percent of the time while thirty miss it 4 percent. That bound assumes the runs are independent and `p` is stable; reusing a seed, a warm process, or fixed scheduler conditions correlates the interleavings sampled, so the real miss rate runs higher than `(1-p)^n` and detection falls short. Vary the seed and scheduler conditions, and prefer a fresh process per run where the interleaving is the thing under test. When thirty runs of a whole file cost too much, narrow the selection to the affected class or test and keep the count, because sample size is what buys detection and scope is what costs time.
13. **When a first fix does not clear a concurrency failure, record which assertion fails before proposing a second cause.** A hypothesis that is plausible and also true can still be insufficient, and only the failure text separates the two. Measured: merging a `ThreadPoolExecutor` into `scripts/maintenance/gc_worktrees.py` left the full 85-test set green on the first run and then produced seven failures in twelve under stress; adding a lock to an unsynchronised read-modify-write in the test's fake clock was a real defect and a real fix and still left eleven failures in twenty; reading the failure text showed one test failing on identity and never on cardinality, and re-pinning that one assertion gave twenty-five clean runs in twenty-five. The repair generalises to what a pool actually invalidates, which is **order** and not identity. Assert the expected set, or the multiset where duplicates are part of the contract, together with the per-item invariant. Fall back to cardinality alone only where identity is itself nondeterministic, because cardinality plus a generic invariant accepts two copies of one item where one of each was required. Worked example in PR #4294.

12. **A test MUST NOT let a fixture supply the precondition the code under test is required to establish**. When the behaviour under test is "this creates X", the test MUST assert X is absent before acting. Substituting a fixture-provided path, a pre-made directory, a seeded record, or an already-open connection makes the assertion pass against code that never does the work, and the test then certifies the opposite of what it claims. Measured: a test for a printed recovery command substituted pytest's `tmp_path` for the destination placeholder. `tmp_path` is created by the fixture, so the `cp` into it succeeded, the test passed, and the real command failed with `No such file or directory` in exactly the two cases it existed to handle, because `git checkout-index --prefix=` creates the destination only when it writes at least one file. The fix asserts the substituted path does not exist, which makes the same substitution impossible to repeat silently.

## SHOULD

1. **AAA pattern**. SHOULD follow Arrange, Act, Assert structure for readability.
2. **Descriptive names**. `Describe`, `Context`, `It` (Pester) and test function names SHOULD describe the behavior under test, not the implementation.
3. **Mock at boundaries**. SHOULD mock external dependencies (HTTP, filesystem, shells); avoid mocking domain logic.
4. **Mirror obligation on contract changes**. SHOULD grep for tests asserting old contracts (signatures, return types, error shapes) and flip them in the same diff, per `.agents/governance/TESTING-RIGOR.md`.
5. **Isolate process-global state in a subprocess**. A regression guard that asserts on process-global state (`sys.path`, `sys.modules`, `os.environ`, `cwd`) SHOULD run in a clean subprocess when the property under test can be masked by another test module's import-time mutation. Sibling modules under `tests/` insert directories on `sys.path` at collection, so an in-process guard for the *absence* of such an entry passes for the wrong reason and stops catching the regression it was written for. Exemplar: the subprocess-isolated lazy-import guard in `tests/validation/test_pre_pr_model_pin_wiring.py` (#3073), whose earlier in-process form passed with the bug reinstated because sibling portability tests kept `scripts/validation` on `sys.path`.
6. **Prove the wiring, not only the guard**. A shared guard, gate, or validator that several call sites depend on SHOULD have a test per consumer that drives the consumer's real entry point and fails when that consumer stops calling the guard. Unit tests on the guard prove the guard; they cannot prove any call site reached it, so a guard can pass every one of its own tests while a consumer is not wired to it at all. Drive the consumer twice over the same input, differing only in the condition the guard rejects, so a consumer that fails for an unrelated reason fails its own control too. Exemplars: `tests/validation/test_pre_pr_model_pin_wiring.py` (#3073) and `tests/validation/test_rule_activation_coverage_wiring.py`. Evidence: the baseline-diffability guard written for issue #4244 passed nine mutations against its own tests while one of its three consumers was never wired to it, and only a per-consumer test found that. The sweep is recorded in the Evidence section of PR #4233, which is where the guard and its wiring tests landed. A second instance: `check_skill_md_portability.py` shipped without calling the guard in `portability_baseline.py`, and the guard's own unit tests passed throughout because none of them could observe whether any call site reached it (#4252).
7. **Prove a guard fires before the effect it guards, not merely that it raised**. A negative test SHOULD end with an isolating assertion that the guarded side effect never happened, because `pytest.raises` alone passes when the code performs the effect and then raises. Exemplar: `test_copilot_complete_rejects_assistant_role` in `tests/eval/test_providers.py` closes with `assert "argv" not in seen`, which fails if the provider shells out before validating; the `pytest.raises` block above it passes either way.
8. **Delete `__pycache__` between a mutation and its rerun.** MUST 7 governs how a harness detects that a patch applied; this is the separate failure that survives every one of those checks. CPython's default `.pyc` invalidation compares the source modification time truncated to whole seconds and the source size, so any same-second edit that preserves size leaves the cache valid and the interpreter runs the previous bytecode. Both directions bite: apply a mutant and the suite may execute the original, so the mutant appears to survive a test that would have killed it; revert the mutant and the restored file may still execute as the mutant, so the next measurement is polluted. Measured on CPython 3.14.6 with real edits and no `utime`, the revert direction reproduced 10 times out of 10. The byte-level checks all pass because the bytes really did change; the interpreter simply never read them. Deleting the cache directory is the remedy. `PYTHONDONTWRITEBYTECODE` and `python -B` do not help, because they suppress writing new bytecode while still reading a stale entry the interpreter considers valid, and pytest's `-p no:cacheprovider` governs `.pytest_cache` only. Hash-based invalidation (PEP 552 `CHECKED_HASH`) does detect the change, but it is not the default, so do not assume it. Applies equally to an ad-hoc control run by hand, where no harness is enforcing MUST 7 for you: a control that cannot be shown to have reached the interpreter is not evidence about the test.
9. **Search for existing coverage by mutation, not by name.** Before adding a test, or restoring one a merge dropped, SHOULD break the behavior and run the suite. The tests that fail are the ones that already guard it. A grep for a class or function name answers a different question: whether a *particular spelling* exists. Trunk routinely reaches the same guarantee under a different name, and an empty grep then reads as absent coverage. Measured: a merge flattened a commit that had added `TestBotSkipClassification` pinning a security gate as unconditional. Grepping trunk for that class returned nothing, so the coverage looked lost and a 121-line restore was staged. Re-adding the guard condition to the workflow and rerunning the file failed three tests, two of them in trunk's `TestBotSkipGuardClassification`, which handles compound `${{ a && b }}` conditions the dropped class would have missed. The restore would have shipped duplicate and weaker tests. The mutation named the real guardians in one step and cost one command.
10. **Pick an input the unfixed implementation gets wrong, then prove it by restoring the defect.** A regression test SHOULD be justified by an input on which the fixed and unfixed implementations disagree, and that justification SHOULD be demonstrated by putting the defect back and watching this test fail. Coverage cannot stand in for that demonstration, and neither can branch counting: in a short-circuit disjunction the defective operand executes, yields the wrong value, and the sibling operand supplies the right answer anyway, so the line is covered, the branch is taken, and the assertion holds. Measured on `is_occupied` in `scripts/maintenance/worktree_occupancy.py`, which read `cwd == path or cwd.startswith(path.rstrip("/") + "/")` and normalized the base on the right side only. The test named for exactly that defect, `test_a_trailing_slash_on_the_worktree_path_is_tolerated` in `tests/test_gc_worktrees_occupancy.py`, passed with the defect present: its cwd was a subdirectory, which the prefix branch matches whether or not the left side is normalized. The sole discriminating input is a cwd equal to the worktree root, and it failed on the first run once added, while the control showed the original test passing either way. The uncovered case reported a live worktree vacant and eligible for deletion (#4257, PR #4294). A test named for a behavior it cannot observe is worse than no test, because it also persuades the next reader not to write the real one.
11. **Dispatch a subprocess fake on its argument vector, not on call order.** A `side_effect` list keyed by position SHOULD be replaced by a callable that inspects `argv` and returns the response for that command, raising a named `AssertionError` on any command it was not given a response for. A positional list encodes an assumption the test never states and cannot check: that the code under test issues exactly these calls in exactly this order. When a branch skips one call, every later entry shifts up by one and is consumed by the wrong command, and the test keeps passing whenever the borrowed value happens to be type-compatible. The `# git branch` style comments that label such lists drift silently at the same moment, so the list then documents an order the code no longer follows. Measured in `tests/test_new_pr.py`: `main()` in `new_pr.py` guards its `git branch --show-current` call behind `if not head:`, so every test passing `--head` skipped it, the entry labelled `# git branch` was consumed by the next call instead, and three separate lists broke again the moment a new subprocess call was added ahead of them. A dispatcher keyed on argv absorbed both changes without edits and turned an unstubbed command into a named failure rather than a `StopIteration` from an exhausted list. Order is not lost, it is promoted: a positional list enforces order invisibly, as a side effect of index alignment that no assertion names and no failure message explains, so when order is itself the property under test, assert it on `mock_calls` after the act, where a reordering fails on the assertion that says so.

12. **Strip CI-only environment variables from a subprocess env built from `os.environ`.** A test that spawns the script under test with `env={**os.environ, **overrides}` inherits every variable the runner sets, and the script may branch on one of them. The test then passes on every developer machine, where the variable is absent, and fails only in CI, where it is always present. Drop the inherited value unless the case under test names it explicitly. Measured: the three stdout assertions in `tests/ci/test_write_copilot_synthesis_summary.py` failed on GitHub Actions and passed locally; the script writes to `$GITHUB_STEP_SUMMARY` when that variable is set and to stdout when it is not, and Actions always sets it, so the tests named for the stdout path never exercised it in CI. Setting the variable locally reproduced the same three failures by name, and popping it when the case does not supply it made all seven tests pass in both environments. Re-running `tests/ci` with `GITHUB_STEP_SUMMARY`, `GITHUB_OUTPUT`, and `GITHUB_ENV` set surfaced no other affected test against a control run without them, so the remedy belongs in the helper, not in a global fixture.

13. **Read `CI` at import time, never inside a test body.** `tests/conftest.py` installs an autouse `_clear_ci_env` fixture (issue #4380) that calls `monkeypatch.delenv("CI")` before every test under `tests/`, so `os.environ.get("CI")` in a test body returns `None` even on GitHub Actions. Any `if os.environ.get("CI")` branch inside a test is dead code, and a guard built on one skips forever instead of asserting. This is the inverse of rule 12: rule 12 is about a variable leaking *into* a subprocess, this is about one being scrubbed *out of* the test process. Capture it in a module-level constant and gate with `@pytest.mark.skipif`, because both module scope and skipif evaluate at collection time, before the fixture runs. Measured: a CI-only guard in `tests/build_scripts/test_generate_hooks_runtime_contract.py` skipped under `CI=1 pytest`, and a control confirmed `CI=1 uv run python -c` did see the variable, so propagation was not the cause. Moving the read to module scope made the same guard run and fail against a mutant that removed every bash candidate.

14. **Do not assert a function's own return literal, and treat deleting such an assertion as half the fix.** An assertion that no input can falsify SHOULD be replaced rather than merely removed. Comparing a returned dict's key set against a hardcoded set, when the function builds that dict as a literal, holds unconditionally and still reads as a contract test. This is the degenerate case of rule 10: rule 10 asks for an input on which the fixed and unfixed implementations disagree, and this asks whether any input can move the assertion at all. The naive probe is wrong, because a parser that raises on unrecognized input still fails on garbage, so asking whether the test would survive unrelated content returns a false negative; ask instead what surviving input makes the assertion false. Deletion is only half the fix because the assertion existed where someone believed a surface needed coverage, so measure what the surviving tests actually cover before removing it: a parser with five patterns and one fail-closed test leaves four free to fail open. Then prove the replacement discriminates by mutating the code and confirming the failure count matches the number of cases expected. Measured: a fail-open mutation of a five-pattern parser failed exactly five parametrized cases, where the single-case test it replaced caught one and the deleted key-set assertion caught none (PR #4485).

15. **A catch-all fallback erases every specific case that shares its value.** When a lookup gains a total fallback so no input can crash it, any entry in the table whose value equals the fallback's becomes behaviorally dead: adding it and deleting it produce identical output, so a test named for that entry passes whether or not the entry exists. The cheap check is to delete the entry and rerun the suite; if it stays green, the entry has no test and never had one. The fix is not to drop the fallback or the entry, both of which carry meaning, but to make the two paths observably different, and diagnostics is the discriminator you wanted anyway: a decided mapping is settled and stays silent, while an unrecognized token is a gap in the table and says so on stderr, which is what surfaces the next producer that grows a token the adapter never learned. Measured on `agent_signal` in `scripts/quality_gate/external_signal_gate.py` (#4487), where `DID_NOT_RUN` and the fallback both yield `UNKNOWN`: with both paths silent, deleting the alias left every test green; after splitting them, deleting it fails exactly one test on the presence of the warning. Where a warning is wrong, use a counter or a result that names the branch. Asserting on the return value alone is what does not work.
16. **Cost a function-scoped autouse fixture at suite scale: multiply its per-call cost by the collected-test count, not by one test's profile.** A subprocess call in such a fixture runs once per collected test. Preserve per-test attribution by optimizing the operation, not by widening the fixture's scope past function level; a session- or module-scoped fixture cannot tell you which test caused the effect. Measured: two `git rev-parse HEAD` subprocess calls per test across 23,706 collected tests cost roughly 72s before any test body runs. Evidence: `.agents/sessions/2026-08-06-session-10003-profile-optimize-pre-submit-pre-commit-pre-push.json`.
17. **A control that cannot fail is not a passing control.** MUST 7 makes a harness distinguish DID-NOT-APPLY from SURVIVED, and SHOULD 10 asks a regression test to be justified by an input the unfixed implementation gets wrong. Neither covers the probe itself. Two mutations with opposite required outcomes are in play, and reading one result against the other's expectation is the trap this item exists for. An **inverted control** (MUST 11) is a deliberately inert edit whose required outcome IS SURVIVED. A **discrimination probe** is an edit that must change what the case observes, so its required outcome is DEAD. Neither result is self-validating. For a probe, name the surviving input that would make its assertion false; if none exists the probe is unfinished rather than passing, and its SURVIVED is a finding about the probe rather than a result about the code. For an inverted control, survival is the pass condition and therefore evidence of nothing by itself, so pair it with a discriminating edit that must be DEAD. The failure is invisible to inspection either way, because a non-discriminating probe looks exactly like the obvious probe for the behavior in question. Measured twice in PR #5176. A discrimination probe for an inverted control flipped `[ "$TIER" != "T1" ]` to `!= "T9"` while the case under test ran `tier="T3"`; T3 is neither T1 nor T9, so the edit was behavior-preserving by construction and the probe passed having measured nothing. Flipping `[ "$AUTO_MERGE" != "null" ]` to `=` instead failed both parameterizations and established the property. Separately, a test for a comment-skip guard used prose that merely mentioned the syntax the guard rejects, and the extractor never reads a line carrying no `jq` token, so deleting the guard under test changed nothing and the test passed anyway; putting a real `jq` invocation inside the comment made the same deletion fail it.

## MUST NOT

1. MUST NOT rename a test to silence a failure.
2. MUST NOT add `Skip` or `@pytest.mark.skip` without a linked issue tracking re-enablement.
3. MUST NOT suppress protocol validation in tests (investigation exemption is narrow; see ADR-034).
4. MUST NOT leave files in the repository working tree. Durable fixtures go in `.pytest_tmp/`, which `.gitignore` covers and `validate_plugin_manifests.py` prunes; ephemeral scratch goes through `tempfile`. A test that deliberately exercises a repo-local `TMPDIR` may use `.pytest_cache/` (see `tests/test_pytest_repo_local_temp_roots.py`). Near-miss spellings such as `.pytest-tmp` are neither ignored nor pruned. Fix at the write target, not with `monkeypatch.chdir`.
