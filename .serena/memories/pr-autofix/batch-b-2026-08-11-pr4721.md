## Load-bearing finding: `get_pr_checks.py` and `why_pr_blocked.py` can report a false green

At 18:13:22Z, with head `cff4f397931579491f95a891472f2160be48e852`:

- `get_pr_checks.py` reported `AllPassing: True`, `FailedCount: 0`, `FailedRequiredChecks: []`, 118 checks.
- `why_pr_blocked.py` reported `FailingRequired: []`, `PendingRequired: []`, `HasBlocker: false`.
- `test_pr_merge_ready.py` reported `CanMerge: true`.
- GitHub reported `mergeStateStatus: BLOCKED` and rollup `state: FAILURE`.

The raw GraphQL `statusCheckRollup` held 160 context runs against 118 unique
names. Three names had two runs each, and the **required** context
`Run Python Tests` had `SUCCESS` at 18:07:08Z (pull_request event, run
31520094673) and `FAILURE` at 18:07:50Z (push event, run 31520090529). The
helpers collapse duplicate context names to one run, so the failing push-event
run hid behind the passing pull_request-event run of the same name. GitHub
evaluates the latest run per context, so the merge was genuinely blocked.

**Rule**: `mergeStateStatus: BLOCKED` with every helper reporting green is the
tell. `BLOCKED` means a protection rule blocks the merge; `UNSTABLE` is the
value that means "merely non-passing status". Never resolve that contradiction
in favor of the helpers. Page the full rollup, group by context name, resolve
the latest run per name, and compare against the ruleset's required list from
`gh api repos/<owner>/<repo>/rules/branches/main`.

## Why the two runs disagreed on identical code

A `push` event builds the branch tip. A `pull_request` event builds the merge
ref (branch merged with base). The failing step was
`Run subprocess encoding count ratchet (whole tree, non-PR)`:

> subprocess encoding count ratchet: BASELINE ABOVE BASE. This tree records 253,
> FETCH_HEAD records 238 (+15). ... If this branch did not edit the baseline, it
> is behind FETCH_HEAD: merge or rebase to pick up the lowered value.

`scripts/ci/subprocess_encoding_count_baseline.txt` was 253 at the merge-base
and 253 at the branch tip (so the branch never edited it) while `main` had
lowered it to 238. The merge ref already contained 238, so the PR-event run
passed. Only merging `main` fixes the push-event run; a re-run cannot.

## Base refresh re-triggers QA report staleness

`scripts/validate_session_json.py` -> `post_qa_code_changes` in
`.claude/lib/qa_report.py` lists non-evidence paths in `qaCommit..HEAD`.
`QA_EVIDENCE_PREFIXES` is `(".agents/memory/episodes/", ".agents/qa/",
".agents/sessions/")`. Merging `main` therefore always re-stales the QA report,
because the merge drags in code paths after the QA commit.

Remedy (established on this branch by commit `cff4f39793`, repeated here):
rebind `qaCommit` in the QA report, `endingCommit` plus the `changesCommitted`
and `validationPassed` evidence strings in the session log, add a `workLog`
entry, regenerate the episode with
`.claude/skills/memory/scripts/extract_session_episode.py <session> --preserve`,
then commit only those three evidence paths. An evidence-only commit cannot
re-stale itself because every path it touches is filtered out.
